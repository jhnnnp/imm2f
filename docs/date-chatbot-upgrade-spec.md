# 데이트 챗봇 고도화 개발 명세

## 목표와 현재 기준

2026-09-23 실사용 평가 기준은 기능 58점, 장소 추천 26점, 동선 45점, UI·시인성 48점, 가독성 36점, 대화 완성도 33점이다. 목표는 문장을 더 그럴듯하게 만드는 것이 아니라, **요청에 맞는 검증된 장소를 고르고, 경험이 겹치지 않는 코스로 연결하며, 수정 요청 후에도 의도를 보존하는 것**이다. 모든 점수는 동일한 평가 세트로 재측정한다.

관찰 사례: `왕십리에서 저녁 먹고 예쁜 카페와 공연장 데이트 코스`는 생성되었으나 카페의 공간적 매력을 뒷받침하는 근거가 없었다. 식당 변경은 기존 공연장·카페를 보존했다. 이어서 일정 추가는 칼국수 식당 다음에 냉면집을 넣었다. 화면 너비 1280px에서 챗봇 패널은 320px이었다. `문화 공연로` 같은 어색한 문구와 `확인 가능한 장소로 구성`이라는 일반론도 노출되었다. 이 사례를 회귀 평가의 첫 항목으로 고정한다.

## 구현 원칙

- 장소 검색 결과의 이름·분류·좌표만으로 `예쁜`, `맛있는`, `공연 중`, `예약 가능`을 단정하지 않는다. 확인된 사실, 사용자의 취향 추론, 확인되지 않은 정보를 데이터와 문장 모두에서 분리한다.
- LLM은 의도 해석, 후보 비교, 설명 작성을 맡고, 장소 식별·하드 제약·일정 수정의 성공 여부는 결정적인 코드가 검증한다. 검증 실패 결과는 기존 코스를 덮어쓰지 않는다.
- 공연장과 그날 볼 수 있는 공연, 카페와 보드게임 카페, 한 끼 식사와 미식 투어는 서로 다른 역할이다. 이름이 비슷한 인근 업장을 원래 장소로 대체하지 않는다.
- 실제 경로 데이터가 없으면 `직선거리`라고 표시하고 보행 시간이나 이동 편의를 추정 사실처럼 쓰지 않는다.

## 순차 작업

### 0. 평가 기준과 장애 관측 고정 — P0

**작업:** 실제 실패 대화를 익명화해 60개 이상의 고정 요청 세트를 만든다. 신규 코스, 장소 교체, 일정 추가·제외, 특정 공연/영화, 예쁜 카페, 음식 취향, 이동 약자, 영업시간 미확인, 장소명 유사성, 검색 실패를 포함한다. 요청마다 기대 역할, 보존할 장소 ID, 금지 중복, 근거 필요 속성을 기록한다. 파이프라인에 요청 ID와 `intent → 검색 → 검증 → 코스 선택 → 응답` 단계별 시간·후보 수·탈락 사유·fallback 사유를 남긴다. 비밀키·로그인 정보·대화 원문은 로그에 넣지 않는다. 현재 개발 서버의 HMR/캐시와 실제 서빙 코드 버전을 확인해 화면에 옛 거리 문구가 남는 문제도 재현한다.

**완료 기준:** 같은 입력으로 현재 버전과 변경 버전을 비교할 수 있고, 실패 원인이 검색 부족/장소 분류/코스 검증/LLM 응답/화면 중 어디인지 드러난다. 이 단계는 점수 상승보다 측정 가능성을 확보한다.

### 1. 의도와 일정 수정 계약 재설계 — P0

**작업:** `DateIntent`를 `지역·출발점`, `필수 경험(식사/카페/공연 등)`, `선호 분위기`, `음식·예산·이동 제약`, `피할 것`, `수정 대상`, `추가할 경험`의 구조화된 필드로 만든다. 사용자 명령은 하드 제약과 선호 점수로 구분한다. 기존 코스는 단순 문장 재해석 대신 장소의 고유 ID·역할·위치를 보존한다. `식당 변경`은 식당 슬롯만, `카페 변경`은 순수 카페 슬롯만 대체한다. `일정 추가`는 새 역할을 명시하거나, 맥락상 합리적인 **새 경험**을 제안한다. 불명확하면 `산책/전시/디저트 중 무엇을 더할까요?`처럼 한 가지 짧은 질문을 한다. 완료 전후의 코스 차이를 검증하고 실패 시 이전 코스를 유지한다.

**코드 위치:** `src/features/ai/dateBrief.ts`, `dateCourse.ts`, `editCurrentCourse.ts`, `actions.ts`, `src/lib/openai/interpretDateRequest.ts`.

**완료 기준:** 식당 교체 후 공연장·카페 ID가 유지된다. 카페 교체에 보드게임 카페가 들어가지 않는다. 일반적인 일정 추가에서 식사 뒤 또 다른 식사가 들어가지 않는다. 성공 메시지 뒤에 장소 수와 역할이 실제로 변하며, 실패는 이유를 알려준다.

### 2. 장소 정보와 추천 근거 구축 — P0

**작업:** `VenueFact`를 장소 ID·지점명·주소·좌표·원천·확인 시각·신뢰도·역할·시그니처 경험으로 구성한다. 음식점에는 대표 음식/분위기, 카페에는 공간·뷰·디저트/음료·체류 적합성, 명소에는 볼거리, 공연에는 `공연장 ID`와 별도의 `공연 ID/날짜/회차`를 둔다. 카카오 장소 검색은 장소 식별과 기본 분류의 원천으로 쓰고, 미감·맛·실제 공연 여부는 별도 근거가 확인될 때만 부여한다. 소스 URL이 있다는 이유만으로 문장 전체를 사실로 승인하지 않도록 `근거 문장 ↔ 장소 지점 ↔ 속성`을 연결한다. 역할별 후보 풀과 최소 후보 수를 확보하고, 지점명이 비슷한 주변 카페와 공연장을 주소·분류·ID로 구별한다. 캐시 갱신 주기는 영업·공연 정보의 변동성에 맞춰 나눈다.

**코드 위치:** `src/lib/openai/designDateDiscovery.ts`, `enrichDateVenues.ts`, `src/lib/kakao/dateCandidate.ts`, 공연 데이터용 신규 어댑터.

**외부 데이터 검토:** [카카오 로컬 API](https://developers.kakao.com/docs/ko/local/dev-guide)는 ID·분류·주소·좌표·상세 URL을 제공한다. [KOPIS 공연 Open API](https://kopis.or.kr/upload/openApi/%EA%B3%B5%EC%97%B0%EC%98%88%EC%88%A0%ED%86%B5%ED%95%A9%EC%A0%84%EC%82%B0%EB%A7%9DOpenAPI%EA%B0%9C%EB%B0%9C%EA%B0%80%EC%9D%B4%EB%93%9C.pdf)는 공연 목록/상세를 검토할 출발점이다. 실제 적용 전 사용 조건·호출 한도·지역 커버리지·갱신 시점을 확인한다.

**완료 기준:** `예쁜 카페` 추천 카드에는 확인 가능한 공간 특성 또는 `분위기 정보 미확인`이 표시된다. `소월아트홀` 요청을 `할리스 소월아트홀점`으로 충족 처리하지 않는다. 공연을 추천할 때 공연장만 찾은 경우에는 그 사실을 명시한다.

### 3. 코스 설계와 경험 다양성 강화 — P0

**작업:** `evaluateCourse`에서 하드 제약을 먼저 통과시킨 뒤, 후보 코스의 장소 품질·사용자 취향 적합도·경험 다양성·동선·증거 수준을 점수화한다. 기본 코스에서는 메인 식사 1곳, 카페 1곳을 권장하고, 명시적 미식 투어/카페 투어가 아니면 동일 역할·동일 음식 계열의 중복에 큰 페널티 또는 금지를 적용한다. `칼국수 → 냉면`과 `카페 → 프랜차이즈 카페`를 회귀 사례로 만든다. 단순 장소 수 증가와 실제 경험 추가를 별도의 성공 조건으로 검증한다. LLM 초안·수정안·fallback 모두 동일한 검증기를 통과시키며, 통과하지 못하면 임의로 장소를 끼워 넣지 않는다.

**코드 위치:** `src/features/ai/courseDesign.ts`, `src/lib/openai/recommendDatePlan.ts`, `src/features/ai/actions.ts`.

**완료 기준:** 고정 평가 세트에서 필수 역할 누락, 다른 업종 대체, 동일 지점 중복, 의도하지 않은 식사/카페 중복이 0건이다. `일정 추가`는 새 경험을 실제로 늘리거나, 가능한 후보가 없음을 구체적으로 알린다.

### 4. 실제 이동 기준으로 동선 재평가 — P1

**작업:** 최종 후보 3~5개만 실제 길찾기 데이터로 재평가하는 2단계 최적화를 한다. 1차는 좌표로 넓게 추리고, 2차는 보행/대중교통 적합 경로의 거리·소요·우회율·강 건너기·역 출입구 등 제공 가능한 필드를 비교한다. 현재 `src/app/api/map-route/route.ts`는 지도 선형을 반환하지만 코스 선택에 검증된 이동 거리·시간을 공급하지 않는다. 도보/대중교통 제공자, 이용 조건, 호출 비용을 먼저 확인하고 전용 `RouteLeg` 어댑터를 만든다. 경로 조회 실패는 명시적으로 직선거리 표기로 낮추며, 이동 시간을 조작하지 않는다. 코스 순서를 변경할 때 사용자의 `먼저 공연` 같은 순서 제약은 보존한다.

**완료 기준:** 지원 지역의 검증 표본에서 카드 거리와 지도 경로가 같은 데이터에 근거한다. 실제 경로가 없으면 직선거리로 표기된다. 동선 점수는 직선거리 합계만으로 결정되지 않는다. [카카오모빌리티 개발자 문서](https://developers.kakaomobility.com/)의 제품별 지원 범위와 제휴 조건을 확인한 뒤 공급자를 결정한다.

### 5. 응답 품질과 실패 처리 개선 — P1

**작업:** 답변을 `코스의 한 줄 이유 → 각 장소의 선택 이유 → 이 순서가 좋은 이유 → 확인이 필요한 정보`로 구성한다. 선택 이유는 검증된 장소 속성과 사용자 요청을 연결해야 한다. `이 카페는 예뻐요`나 `확인 가능한 장소` 같은 무의미한 일반론, 불필요한 반복 카테고리·주소, 어색한 조사/어미를 제거한다. 장소 비교에서 탈락한 후보와 차이도 내부 판단 근거로 남긴다. 공연 일정이나 영업 상태처럼 확인하지 못한 내용은 자연스럽게 확인 필요 항목으로 보여준다. 모델 오류·시간 초과·근거 부족은 각각 다른 사용자 메시지로 처리하고, 낮은 품질의 fallback을 AI 완성 코스로 포장하지 않는다.

**코드 위치:** `src/lib/openai/recommendDatePlan.ts`, `composeDateChat.ts`, `src/features/ai/chatRoute.ts`.

**완료 기준:** 사람이 평가하는 고정 샘플에서 장소별 설명의 80% 이상이 해당 장소의 확인된 속성 하나와 사용자 요청 하나를 명시적으로 연결한다. 사실 근거 없는 미감·맛·예약 가능 주장 0건, 어색한 한국어 문장 사례 0건을 목표로 한다.

### 6. 챗봇 전용 화면 재구성 — P1, 1~5단계와 독립적으로 먼저 반영 가능

**작업:** AI 패널이 열린 경우에만 데스크톱 그리드를 넓힌다. 현재 `src/app/globals.css`의 `.app-shell:has(.ai-editor)` 규칙 뒤에 `.app-shell:has(.activity-feed)`가 선언되어 숨겨진 피드가 있는 화면에서도 320px 규칙이 우선된다. 선택자·선언 순서를 정리하고 AI가 없는 다른 페이지의 폭을 유지한다. 1280px 화면 목표 패널 폭은 최소 480px, 가능한 레이아웃에서는 약 520~600px로 잡되 본문 최소 폭과 함께 검증한다. 카드 내부는 제목·한 줄 핵심 이유·근거·이동·상세 링크의 시각적 계층을 만들고, 중복 메타데이터를 접는다. 본문 15~16px, 보조 정보 13~14px, 충분한 줄간격·문단 간격, 명확한 로딩 단계를 적용한다. 390/768/1280/1440px에서 확인한다.

**코드 위치:** `src/app/globals.css`, `src/features/ai/components/AIPlanEditor.tsx`, `src/components/layout/ContextPanelDrawer.tsx`.

**완료 기준:** 1280px에서 패널 실측 폭 480px 이상, 다른 페이지 기존 레이아웃 유지, 모바일 가로 스크롤·텍스트 겹침 0건. 장소 5곳 코스에서도 핵심 이유와 수정 버튼을 읽고 찾을 수 있다.

### 7. 품질 게이트와 출시 — P0/P1 종료 조건

**작업:** 단위 테스트는 역할 분류·지점 동일성·추가/교체 불변식에 집중한다. 통합 테스트는 검색→근거→코스 선택→응답과 외부 API 실패를 검증한다. 고정 프롬프트 평가에서 기존 버전과 새 버전을 사람이 블라인드 비교하고, 실제 화면 크기별 시각 회귀 및 로그인 후 읽기 전용 시나리오를 확인한다. 모델·검색 호출 수, 비용, 응답 지연을 기록하고 캐시/병렬화로 조정한다. 배포는 제한된 사용자부터 시작하고 실패율·수정 성공률·품질 평가를 비교해 확대한다.

**출시 기준:** 지원 범위 내 코스 생성 성공률 95% 이상, 수정 성공 응답 후 불변식 위반 0건, 필수 역할 누락 0건, 장소 추천 사람 평가 평균 70/100 이상, 전체 사람 평가 80/100 이상을 목표로 한다. 첫 코스 P95 30초 이내, 단일 수정 P95 20초 이내를 목표로 하되 실제 공급자 지연을 측정해 재설정한다. 수치 미달이면 실패 샘플을 분류해 해당 단계로 되돌린다. 점수만 올리고 사용자에게 잘못된 사실을 제시하는 변경은 출시하지 않는다.

## 2026-09-24 장소 조사 보강 및 실측
