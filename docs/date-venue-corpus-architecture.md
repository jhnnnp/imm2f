# 데이트 장소 자료집 구축 설계

> 이 문서는 특정 지점의 검증 근거를 보조적으로 축적하는 파일럿이다. 데이트 엔진의 주 RAG는 장소 전체를 저장하는 방식이 아니라 [데이트 코스를 짜는 공략집](./date-engine-playbook.md)을 검색하는 방식이다. 새로운 지역의 장소·공연은 요청 시 공급자에서 찾는다.

## 현재 병목

2026-09-25 작업 시작 시 공유 `venue_evidence`에는 22개 근거 문장, 18개 지점만 있었다. 코스 요청 시 카카오 검색은 빠르지만 새로운 동네의 공간·메뉴·경험 근거를 실시간 웹 조사로 확보하려고 하면 공급자 타임아웃과 낮은 지점 일치율 때문에 20~30초가 걸린다. 장소가 많아도 근거가 없는 후보를 비교하면 추천 품질은 올라가지 않는다.

## 목표 구조

1. **장소 식별 계층:** 카카오 등 공급자의 장소 ID, 정확한 지점명·주소·좌표·분류를 정규화한다. 이름이 비슷한 카페와 공연장은 같은 장소로 합치지 않는다. 폐업·이전·동명이점은 별도 상태로 관리한다.
2. **근거 계층:** 현재 `venue_evidence`를 확장해 `지점 ID → 속성(space/menu/experience) → 짧은 사실 → 출처 URL·원문 발췌·확인 시각·검증 상태`를 보관한다. 출처가 특정 속성을 뒷받침하지 않으면 추천 이유로 사용하지 않는다. 협찬 후기와 공식·방문 기록의 신뢰도를 구분하며, 검색 결과의 인용은 원문 직접 확인 전까지 `search_report`로 남긴다. 사용자 대화·취향 데이터는 공유 자료집에 저장하지 않는다.
3. **공연 계층:** KOPIS 공연장 ID와 공연 ID·날짜·회차를 분리한다. 공연장만 확인한 경우 당일 공연 추천으로 취급하지 않는다.
4. **수집 계층:** 인기 요청 지역부터 공급자 API로 후보를 수집하고, 이용이 허용된 공식·사업장·공개 편집 자료에서 짧은 속성 근거를 조사한다. 웹 페이지 전문을 복제하지 않는다. 지점명·주소·발췌·속성의 일치 검사에 실패한 결과는 격리하고 재시도 또는 검토 대기 상태로 남긴다.
5. **검색 계층:** 요청 시 지역·거리·역할·날짜·예산의 구조화된 필터를 먼저 적용한다. 검증된 후보가 충분해지면 속성 문장을 대상으로 키워드 검색을 붙이고, 의미가 다양한 질문이 늘 때만 pgvector/하이브리드 검색을 추가한다. 벡터 유사도만으로 장소 ID·영업·공연 여부를 결정하지 않는다.
6. **코스 계층:** 역할별 상위 후보를 비교한 뒤 경험 중복, 취향, 근거 수준, 실제 경로를 평가한다. 선택 근거와 확인되지 않은 정보는 응답에서 분리한다. 수집 작업은 사용자 요청과 별도로 실행해 채팅의 임계 경로에서 웹 조사량을 최소화한다.

## 구축 순서와 게이트

| 단계 | 구현 | 통과 기준 |
| --- | --- | --- |
| 1. 수집 정책 | 허용 공급자·속성·갱신 주기·호출 한도 정리 | 출처와 재사용 범위가 기록된 자료만 저장 |
| 2. 지점 카탈로그 | 카카오 장소 ID 중심 정규화, 분류·좌표·주소 확인 | 지점 오인 0건, 역할 오분류 0건 |
| 3. 근거 사전 구축 | 왕십리·성수·연남·서촌·을지로 파일럿, 역할별 균형 수집 | 각 요청 역할에 비교 가능한 근거 후보 2곳 이상, 사람이 표본 검토 |
| 4. 갱신 파이프라인 | 실패 재시도·변경 감지·만료·폐업/이전 처리 | 만료 근거가 새 사실로 표시되지 않음 |
| 5. 검색·평가 연결 | 지역/역할 필터 → 근거 비교 → 코스/동선 평가 | 고정 평가 요청에서 근거 없는 미감·맛 주장 0건, 코스 품질 향상 |
| 6. 확장 | 실제 검색량을 보고 지역 확대, 필요 시 pgvector 도입 | 검색 지연과 품질이 기존 구조보다 개선됨 |

`venue_evidence`의 현재 7일 검색 보고 만료 정책과 출처·지점 검사 코드는 재사용한다. 다만 대량 수집에는 재시도 큐, 소스별 갱신 주기, 관리자 검토 상태, 중복 제거가 추가로 필요하다. 모델을 재학습시키는 것보다 자료집을 조회해 최신 근거를 주입하는 방식이 우선이다. 파인튜닝은 충분한 평가 데이터가 쌓인 뒤 말투나 의도 분류에 필요할 때만 검토한다.

## 첫 파일럿 결과와 실행

`npm run corpus:build -- 익선동`은 채팅 요청과 별도 프로세스에서 카카오 지점을 찾고, 편집 자료의 장소명을 지점 ID에 재확인한 뒤 속성 근거를 수집한다. `npm run corpus:build -- --pilot`은 왕십리·성수·연남·서촌·을지로를 순차 처리한다. 현재는 일회성 빌더이며, 일정 실행·지속 큐·관리자 검토 도구는 아직 없다. 원문 전문이나 출처가 없는 문장은 저장하지 않는다.

2026-09-25 파일럿 뒤 DB는 **31개 문장 / 26개 지점**이다. 익선동은 후보 24곳 중 2곳, 성수는 32곳 중 2곳, 연남은 32곳 중 1곳, 서촌은 31곳 중 2곳, 을지로는 30곳 중 2곳에만 검증기를 통과한 근거가 있었다. 왕십리는 기존 캐시 포함 32곳 중 12곳(카페 9, 식당 3)이다. 전시 후보는 모든 파일럿 지역에서 0곳이었다. 단순 대량 검색이 곧 양질의 자료집을 만들지는 않는다는 반증이며, 소스별 직접 검증·공식 전시 데이터·관리자 검토와 역할별 후보 큐가 다음 핵심 작업이다. 이 수치로 90점 품질을 주장할 수 없다.

## 운영 지표

- 요청 역할별 근거가 있는 후보 수, 지점 검증 통과율, 속성별 출처 품질
- 실제 추천된 장소의 근거율과 사람이 매긴 적합성 점수
- 캐시 적중률, 실시간 웹 조사 호출 수·실패율·비용, 채팅 P50/P95
- 폐업·공연 회차 오류, 오래된 사실 노출, 코스 수정 불변식 위반

파일럿은 장소 수 자체보다 **검증된 선택지의 밀도**로 평가한다. 자료집이 빈 지역에서는 짧은 조사 예산 안에서 확인된 사실만 설명하고, 부족한 속성은 솔직히 미확인으로 남긴다.
