# 데이트·여행 엔진 공략집 RAG

이 자료집은 **모든 장소를 복제한 카탈로그가 아니다.** 사용자의 요청을 어떻게 조사하고, 후보를 어떻게 비교하고, 어떤 경험을 어떤 순서로 묶을지에 관한 작고 버전이 있는 판단 규칙이다. 실제 장소의 존재·지점·주소·영업 정보는 장소 공급자에서, 공연 회차는 공연 공급자에서 확인한다. 장소별 공간·메뉴 근거가 확보된 경우에만 `venue_evidence`를 보조 자료로 사용한다.

## 요청별 실행 순서

1. **의도 해석:** 동네, 필수 경험, 음식·분위기·예산·이동 제약, 수정 대상을 구조화한다. “공연 보고 저녁”이라는 순서도 보존한다.
2. **공략집 검색:** 요청 문장과 현재 코스 상태에서 태그를 추출한다. `discovery`, `selection`, `editing`, `response` 단계마다 맞는 카드만 우선순위로 가져온다. 예를 들어 “예쁜 카페와 공연”은 공간 특성 검색, 공연과 공연장 구분, 해당 날짜 회차 검증 규칙을 받는다.
3. **실시간 후보 조사:** 공략집이 정한 다양한 검색어로 장소 후보를 모은다. 후보의 정확한 지점 ID·역할을 검증하고, 속성 주장에는 그 지점에 맞는 출처를 연결한다.
4. **코스 비교:** 사용자 하드 제약과 수정 불변식을 코드로 검사한 뒤, 요청 적합성·장소 고유성·경험 다양성·근거·동선을 비교한다. 공략집은 비교 관점이고 장소의 사실이나 강제 제약이 아니다.
5. **응답:** 장소마다 확인된 사실과 취향 추론을 연결한다. 영업·공연·미감이 미확인이면 미확인으로 말한다. 수정 실패 시 기존 코스를 보존한다.

## 저장 및 갱신

`public.date_planning_playbook`은 짧은 규칙 카드를 `id`, `version`, `stage`, `tags`, `required_tags`, `excluded_tags`, `guidance`, `example`, `priority`, `active`로 저장한다. `tags`는 후보 검색을 위한 OR 조건이고 `required_tags`는 모두 충족해야 하며 `excluded_tags` 중 하나라도 있으면 제외한다. 예컨대 날짜가 있는 공연 검증 카드는 날짜와 문화 경험이 함께 있어야 한다. 저장소의 [`datePlaybook.ts`](../src/lib/openai/datePlaybook.ts)가 버전 관리 원본이며, `npm run playbook:sync`로 DB에 발행한다. 서버는 DB 카드를 10분 동안 캐시한다. DB가 실패하거나 새 코드에 필요한 카드가 누락되면 저장소의 규칙을 사용한다. `active=false`로 카드 하나를 비활성화할 수 있다. 브라우저 사용자의 DB 권한으로 카드를 읽거나 수정하지 않는다.

## 결정 우선순위

1. 사용자가 이번 요청에서 명시한 필수·금지 조건과 방문 날짜·순서.
2. 수정 거래의 불변식: 유지 장소의 제공자 ID, 역할, 상대적 순서, 추가·교체 개수. 실패하면 기존 코스를 보존한다.
3. 공급자에서 확인한 행사 회차·장소 정체성과 시간·이동의 실행 가능성. 미확인 정보는 충족으로 계산하지 않는다.
4. 장소별 출처 근거와 두 사람 취향. 검색 요약(`search_report`)은 원문을 독립 대조한 사실로 격상하지 않는다.
5. 경험 다양성과 보행 경로. 같은 수준의 후보를 비교할 때만 선호와 거리 점수를 사용한다.

공략집 카드의 우선순위 숫자는 **검색 순위**이며 위 계약을 뒤집을 권한이 없다. 강제 조건은 `evaluateCourse`와 `courseMutationProblems`의 결정적 검사로 유지한다. 변동 정보(공연 회차·좌석·영업·가격)는 요청 날짜에 맞춰 다시 확인하며, 확인할 수 없으면 답변에서 미확인으로 표시한다. `response` 카드만으로 최종 문구를 보장할 수 없으므로 최종 답변 생성 코드에도 근거가 없는 장소의 미확인 설명과 공연·예산 경고를 둔다.

규칙을 추가할 때는 관찰된 실패 요청, 적용 단계와 태그, 올바른 판단, 반례, 테스트를 함께 기록한다. 새 규칙이 특정 장소의 사실을 만들어내거나 사용자의 명시적 조건을 바꾸면 채택하지 않는다. 규칙이 많아져 태그 검색의 선택 품질이 떨어질 때만 전문 검색 또는 벡터 검색을 비교 평가한다. 현재처럼 34개의 짧은 카드에는 벡터 DB가 필요하지 않다.

## 여행의 별도 계약

`travel`은 1박 이상뿐 아니라 당일치기와 여행 지역의 코스에도 붙는다. 여행은 방문 가치가 있는 목적 경험을 먼저 고르고, 일자별 중심 지역·식사·쉬는 시간을 묶는다. 각 일차는 네 곳 이하이며, 미식·휴양처럼 사용자가 명시한 예외를 제외하면 장소별 출처 근거가 있는 핵심 경험을 적어도 한 곳 포함해야 한다. 근거가 없으면 이름만 그럴듯한 관광지와 식당으로 완성 코스를 만들지 않는다.

축제는 여행 시작일이 아니라 **배정된 일차의 날짜**로 다시 검사한다. 장거리 이동은 직선거리와 이동 수단별 최소 추정으로만 판단하고 실제 도로·환승 시간으로 설명하지 않는다. 숙소와 도착·귀가 교통편이 없으면 숙박 완성 일정이라고 말하지 않는다. 일정을 수정할 때는 명시적으로 옮겨 달라는 요청이 없다면 기존 장소의 일차도 보존한다.

## 품질 평가

공략집 도입 전후에 동일한 요청을 비교한다. 공연장과 공연의 혼동, 보드게임카페의 카페 대체, 식사·카페의 무의도 중복, 추가·교체 후 장소 ID·순서·일차 보존, 장소별 근거율, 사람의 추천 선호도를 측정한다. 테스트 요청은 식사만, 분위기 없는 카페, 날짜 없는 공연, 날짜 있는 공연, 비 오는 날, 예산·접근성 제약, 당일치기, 1박2일, 2박3일, 축제의 2일차 배정, 숙소 미확정, 이전 코스 수정, 공급자 실패를 포함한다. 태그 검색 성공이나 카드 수를 품질 점수로 간주하지 않는다. 60개 고정 요청의 실제 공급자 실행과 블라인드 사람 평가는 별도 출시 관문이며, 단위 테스트 통과로 대체하지 않는다.
